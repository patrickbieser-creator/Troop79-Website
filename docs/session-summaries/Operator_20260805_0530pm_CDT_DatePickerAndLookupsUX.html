What Was Accomplished

Custom calendar date picker, replacing native type="date" app-wide

Built a shared DatePickerField component (react-day-picker) — text input showing the formatted date, calendar-icon trigger, typed-entry parsing, Clear/Today shortcuts, themed with the admin's existing color/spacing tokens. Landed first on the Events lookup editor, verified end-to-end in the browser, then rolled out via six parallel subagents to 14 more files across Roster, Ledger, Fast Entry, Audits, Meetings, Events, and News — 19 date fields total.

Three files were left on the native picker on purpose, not by oversight: two read-only report-filter pages are zero-JS server components with no client state to hang a controlled picker off of, and the public profile's birthdate field is better served by native typed entry than a decades-of-month-paging calendar popup.

Real architecture problem found mid-rollout: native <dialog> top-layer stacking

Seven of the seventeen candidate files render their date field inside a native <dialog> shown via showModal(). Dialogs promote to the browser's top layer, which renders above all normal-stacking-context content regardless of z-index — the calendar popover was rendering behind the open dialog, not above it. Fixed by having the component detect the nearest open ancestor dialog at open-time and portal into it instead of the default target, so it shares the dialog's top-layer promotion while still inheriting the admin's theme tokens. Verified on two different dialogs (Roster's Add Scout, Calendar's Add Entry) before rolling out to the remaining five.

Two more bugs caught by actually using the thing, not just building it

The popover portaling to document.body broke CSS variable inheritance (the admin's color tokens are scoped to a parent element the popover no longer lived inside) — fixed with a dedicated portal target inside that parent. Separately, closing the popover via an outside click updated React state but didn't blur the actual input field, so clicking the same field a second time never reopened it — fixed by also opening on click, not just on focus. Neither was caught by lint, typecheck, or the production build; both surfaced only from driving the real interaction in a browser.

Lookups & Admin: search box unconfused from add

Events, Service Projects, Leadership Positions, Skills, and Tags each had a top text box that silently did double duty — sometimes it filtered the list, sometimes it was the field for a brand-new entry, depending on how many rows the card had, with no visual cue which one you were looking at. That box is now always search; the + Add button reveals a small form (name plus whatever else that item needs — date/type for Events, a checkbox for Skills) with its own Cancel/Add buttons instead of sitting inline permanently. Tags, which had no search at all, was brought onto the same shared filtering pattern as its siblings. Households' add row moved from the bottom of the card to the top, matching where every other card's add action lives.

Decisions

DecisionWhy
DatePickerField portals into the nearest open dialog when one exists Smaller, one-component fix that shares an existing top-layer promotion, instead of rebuilding the popover on the native Popover API and trading one stacking subtlety for another.
Lookups search is opt-in per card, not a global default change Merit Badge Catalog, Internal Requirement Codes, Leader Skills, and Scout Instructors weren't part of the ask — an opt-in flag on the shared hook keeps their existing behavior untouched.
