What Was Accomplished

Patrick's ask, verbatim: keep the date on the left, drop the redundant "Milwaukee, WI" on the right, hide Profile and Log Out unless someone's actually signed in, show who's signed in and at what level when they are, and stop showing two separate sign-in links.

One component instead of four unconditional items

The utility bar used to show Profile, Sign In, and Members Login all the time — regardless of whether anyone was signed in — plus a self-hiding Log Out that was the only one of the four that actually checked session state. A new SiteAuthStatus component replaces all four: a single Member Login link when signed out, or “Signed in as {name} · {Level}” plus Log Out when signed in. Profile now appears only for a verified adult identity session — the one audience the page is actually built for; a scout's verified session or the plain family-password cookie never show it.

Three real access levels, one label each

The site actually has four distinct session mechanisms under the hood (leader/scout shared password, family shared password, and verified passwordless identity split into adult and scout tiers) — but the troop only talks about three things: Admin, Scout, and Family. The new /api/session-status endpoint collapses the four mechanisms onto those three labels, plus a display name when the session carries one.

Not new exposure: the display name shown in the nav (a leader's typed login name, or a verified visitor's name from the passwordless flow) was already rendered server-side on /profile and every /admin page for a signed-in visitor. This just lets the client-side nav show the same thing.

Two sign-ins become one

/signin (passwordless email) is now the single nav entry point. Leaders and scouts still reach their separate shared-password login, but now via a link at the bottom of the Sign In page — “Leader or Scout? Sign in with the troop password” — rather than a second item competing for space in the nav.

Verified live, with one deliberate gap

Checked in the browser: the logged-out state shows exactly one link, and an already-active Family session on this machine correctly showed “Signed in · Family” with no Profile link (the plain family-password cookie isn't the verified-adult tier Profile needs). The Admin/Scout-level branch and the identity-adult Profile case use the identical rendering path already proven live by that Family case, but weren't independently exercised with real credentials — doing so would mean typing LEADER_PASSWORD/SCOUT_PASSWORD into browser automation, which this project's own history (a partially-echoed database password, since rotated) treats as compromising the credential. Left as a 30-second manual check for next time.
