What Was Accomplished

Patrick's ask: show a scout's completed requirements next to each rank row once expanded, highlight completed merit badges on the grid with their date, add a switcher for households with more than one scout, and give designated leaders a way to view the library as any scout in the troop.

Designed before it was built

Given the scope — a new table, cross-cutting UI changes, and a genuinely new access-control capability (leader impersonation) — this went to tech-lead for a design review before any code was written. It flagged a real risk: a leader session only ever carries a display label ("Mike Ba."), never the database code the new superuser table is keyed on, so the resolution had to go through the same label→code lookup the login page already uses. It also caught a gap in the existing rename-cascade list and steered the admin UI into the existing Lookups & Admin card pattern rather than a new standalone screen.

The authorization model

A single resolver — resolveLibraryViewer() — is the only place that decides whose progress renders. The URL carries a ?viewScout= parameter, but it is never trusted on its own: it only picks a scout from a list the session is already authorized to see (a verified household's own kids, or an authorized leader's full active-scout list). Everyone else — anonymous visitors, the shared family password, an unauthorized leader — gets nothing extra, exactly as before.

qa-lead's mandatory security review (any new access-control surface gets one, no exceptions) came back SHIP, with two low-severity fixes folded in: a scout who happens to also hold an admin login no longer loses their own personalization, and the merit-badge detail page's deliberate exclusion is now documented in a comment instead of looking like an oversight.

The superuser proxy is opt-in, on purpose

A leader flagged as a library superuser does not see anyone's progress by default when they land on the page — a leader has no "their own scout" to default to, and silently dropping every leader into someone else's view would be a strange surprise. Instead they see a clearly labeled picker; choosing a scout switches on a "Viewing as {name}" banner with a one-click way back out.

Verified against real data, without touching real credentials

Local Postgres was started fresh for this session and turned out to already hold real production-shaped data (48 scouts, 7 ranks, 69 merit badges) — a stale backlog note claiming it was empty has been removed. All four viewer states (anonymous, a real two-scout household switching between siblings, a scout's own verified sign-in, and the superuser proxy) were exercised live in the browser against that data, using a throwaway dev-only route that mints test sessions server-side rather than typing any shared password into browser automation. The route and all fixture data were deleted immediately after.
