What changed

The site had five ways to grant access across two identity spaces, which is why a leader who was also a parent had to sign in twice. It now has one: a capability granted to a named person. Both shared passwords are gone, publishing became a property of the record rather than a permission, and passkeys landed.

Capabilities replaced roles

  • A capability is a row keyed to a people.id, granted on a new Access & Permissions screen. Knowing a password grants nothing; appearing in a table grants nothing.
  • 182 guards converted across the admin — 129 requireRole call sites plus 53 ensureLeader, the latter inlined rather than renamed so each site states its own authority.
  • person_authz() returns the session epoch and the grants in one round trip, so authorization costs nothing beyond the revocation read already being paid.
The seed nearly handed a youth the roster. leaders.can_login is true for 21 rows — including non-person codes like Summer Camp, and an active scout who teaches. Seeding from that flag would have granted a minor roster.manage: every family's address, birthdates and medical-adjacent notes. The seed replicates the existing adult-person rule instead, guarded by a property test that names nobody.

Both shared passwords retired

  • SCOUT_PASSWORD — never used by a single scout, and the one thing blocking the rest of the conversion. Deleting the role deleted a whole bug class with it: the deny-by-omission allowlist whose own comment recorded that the advancement pages had leaked through it once.
  • LEADER_PASSWORD — retired behind a break-glass CLI that mints a code straight against the database. A script rather than a web path, because an emergency password is a permanently-live endpoint guarding total access. Run and verified before anything was removed.

Publishing is a filter, not a permission

Patrick's reframing, and the better design: whether something is live is a property of the record. Scouts and parents propose a story from the public side, it lands pending, a leader publishes it. Not a new mechanism — change requests, library submissions, proofs and meeting plans all already worked this way. News and the calendar were the odd ones out.

Signing in

  • Find your name instead of remembering your email — the measured blocker was recall, not reachability (all 41 adults in active households are reachable). Search runs server-side and matches the full surname while returning only “Patrick B.”
  • Passkeys — discoverable credentials, adults only, with the emailed code kept permanently as the recovery path.
  • A Members area as the single front door, with the household live and five future services listed openly.

Blockers resolved

ProblemDiagnosis
Sign-in link failed while the code in the same email worked Codes are digits; link tokens were base64url, which is case-sensitive. A mail gateway normalising URL case destroyed one and not the other. Tokens are lowercase hex now.
Public calendar empty everywhere, HTTP 200 Migrations shipped behind the code needing them; loaders dropped error and rendered “no events”. Self-inflicted, ~1 hour, fixed.
Two identical “Michael B.” rows on the sign-in picker On a directory that is cosmetic; on a picker it sends a code to another family's inbox. Reuses the disambiguation the admin login pool already had.
Troop name wrapped to three lines on a phone The masthead was entirely inline styles — no media queries, so it could not respond at all.
“Signed in · Family” shown to people who had not signed in Leftover from demoting the troop password to a gate. The tell was the missing name.
The outage is the lesson worth keeping. An empty page is the worst failure mode available: a 500 is noticed in minutes, an empty calendar looks like the truth. Public list loaders now throw rather than return nothing — with enumeration-safe lookups deliberately exempt, and a test asserting that exemption so a later sweep does not “helpfully” harden them.
