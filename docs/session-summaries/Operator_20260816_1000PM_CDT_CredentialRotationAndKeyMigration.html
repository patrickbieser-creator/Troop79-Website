Both credential exposures are closed. B-002 had been open since July 20 and B-003 since August 7 — flagged, by the tracker’s own note, three sessions running without being done. No application code changed today; the working tree was clean start to finish.

Why this kept not getting done

The blocker notes and the earlier plan both pointed at rotating the project’s JWT secret. That is the operation that makes this job frightening: the legacy anon and service_role keys are both signed by that secret, so rotating re-issues both at once. Production is broken from the moment you click until every consumer is updated and rebuilt — and you are doing that work under an outage, with no way to verify first.

Opening the actual dashboard changed the answer. Supabase had already provisioned its newer publishable/secret key system on this project, and both key sets stay valid at the same time. That turns a tear-everything-at-once rotation into an ordinary migration with a verification step in the middle.

What was done

B-002 — database password RESOLVED

Reset via Database → Settings → Reset password, updated in next-app/.env.local, CLI re-linked. Confirmed beforehand by grep that this had zero production impact: nothing in next-app/src reads the variable and there is no DATABASE_URL anywhere — the app reaches Postgres only through PostgREST. The credential is used exclusively from one machine, for the psql bulk-data recipe and supabase db push. Nothing was redeployed.

B-003 — leaked service_role key RESOLVED

Production moved onto sb_publishable_… and sb_secret_… in Vercel, redeployed, verified against the live site, and only then were legacy JWT keys disabled. The exposed key is now inert.

The verification gap that mattered. While legacy keys are still enabled, a healthy production site proves nothing about which keys Vercel is actually using — both work. Every green check would look identical if the env update had silently failed, and disabling legacy would then take the site down. The only check that distinguishes them is reading the sb_ prefix and the updated timestamp in Vercel’s own environment UI, which was done before proceeding.

Decision recorded

[D-123] Migrate off legacy JWT API keys rather than rotate the JWT secret

  • Zero-downtime — old and new keys overlap, so verification happens while rollback is still free.
  • Reversible — the legacy tab offers “Re-enable JWT-based API keys” afterwards.
  • Future rotations are routine — the secret key is now independent of the publishable one.
  • Local dev unchanged — .env.local points at local Docker, so local and tests still run legacy-format keys while production does not. A prod-only failure should suspect that asymmetry first.
  • Never touch JWT Keys in the left nav — that is the riskier lever this path avoids.
