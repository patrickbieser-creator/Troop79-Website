Both bugs are closed and verified end to end — from real server evidence, not re-testing and hoping. Neither was guessed at: one came from a Vercel runtime-log error message matched byte-for-byte against a library's source; the other came from a direct SQL query proving a fresh token existed while zero requests ever reached the server for it.

Bug 1 — Passkey registration silently accepted no verification at all

The first real passkey attempt failed. Dashlane, asked for userVerification: 'preferred', created a passkey with no fingerprint, PIN, or vault prompt at all — and no on-screen sign that anything had been skipped. The deciding evidence: a second browser’s platform authenticator, asked the identical 'preferred' request, correctly prompted for a PIN. That comparison settled it — ‘preferred’ isn’t unreliable in the abstract, it hands the decision to the authenticator’s own discretion, and at least one real one exercises that by doing nothing.

Why this mattered. A discoverable passkey created with zero verification grants full account access on device possession alone — materially weaker than the feature’s own promise, “signs you in with a fingerprint or your face.”

Bug 2 — The sign-in email link had been pointing at localhost since launch of the feature

A user reported the emailed sign-in link didn’t work. Investigation ruled out the obvious suspects one at a time, from evidence: the token itself was fine (a fresh, valid, unconsumed row existed in login_tokens, confirmed by direct query); Vercel’s warning-level logs showed zero “unknown token” events in 24 hours; and a live-tailed log search showed zero requests ever reaching /signin/verify at all, even while the same browser’s session-status poll kept firing every 10–15 seconds. A link that never leaves the device explains all of it at once — and the user confirmed directly: “the link is going to localhost:3000.”

The root cause was a repeat, not a new mistake. NEXT_PUBLIC_SITE_URL has never been set in Vercel — confirmed directly on the live Environment Variables page (“No Results Found”). This is the exact same bug that shipped once already, on launch day 2026-07-12, in the .ics feed’s Subscribe links — lib/site-url.ts was purpose-built as the fix at the time. The sign-in link, written later for a different feature, never adopted that shared helper and independently reinvented the same naive fallback that had already caused one production incident.

A qa-lead review of the fix then found a third live instance of the identical pattern in scripts/break-glass.mjs — the emergency account-recovery script, arguably the worst place to repeat the mistake, since its output is read down a phone line or texted to someone already locked out. Closed in the same pass.
