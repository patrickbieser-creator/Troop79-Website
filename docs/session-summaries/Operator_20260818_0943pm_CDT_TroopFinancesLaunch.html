What Was Accomplished

Troop Finances — full spreadsheet replacement

Built and shipped five phases in one session: schema, treasurer write UI, family scout-account statements, reimbursement workflow, and an activity report — the treasurer's standalone spreadsheet is no longer the source of truth for troop money.

  • One ledger for every dollar — financial_transactions covers real Landmark checking/savings and notional per-scout/Scholarship Fund sub-balances, with balances always derived via sum(), never stored.
  • Treasurer write UI at /admin/finance — record, void, transfer, monthly reconciliation, CSV export, sort/filter, and (added mid-session) genuine in-place edit, kept distinct from void.
  • Family scout-account statements at /member/scout-account, extending the Resource Library's superuser-proxy pattern to a new domain — Patrick's own account defaults to his family view with a switcher to proxy another scout.
  • Reimbursement workflow start to finish: family submission with receipt upload through treasurer approve/deny/pay, payout atomically linked to the request.
  • Activity Report groups income/expense by event with date range + per-account breakdown — explicitly declined a normalized activities lookup table in favor of a lightweight autocomplete.
  • Dashboard gained Total Funds / Available Funds cards; event-fee roster payments now write a real linked transaction instead of flipping a flag.
646 historical transactions imported and verified twice. Local import matched the spreadsheet's own Dashboard totals to the penny; the production import matched local exactly (checking $2,198.11 / savings $3,079.39 / scout accounts $2,182.13 / scholarship $760.77).

Production deployment

Done live this session, not simulated. Migrations applied via supabase db push (dry-run confirmed first). The historical import hit a real environment constraint: the sandbox's own secret-masking layer breaks any script that reads a production credential via env var. Worked around by dumping the already-validated data out of local Postgres as INSERT statements and applying it through supabase db query --linked — the CLI's own authenticated connection, never a raw key typed into a command.

Production deployment is a mandatory Opus risk-assessment trigger under this project's escalation rules. Spawned before executing — it returned the operation order (migrations → import dry-run → git push) and one required pause (confirm targeting + idempotency before the real write), both followed.

Code committed and pushed; Vercel deploy confirmed Ready, live at www.troop-79.com. Changelog updated to v1.49.0.

Decisions

  • D-134 — Single ledger, no online payments, no dues tracking. Mirrors the project's existing single-table pattern; deferred online payment collection rather than rejecting it.
  • D-135 — Legacy capability shim must explicitly exclude narrow grants. The "grant everything" default for legacy sessions is not automatically safe for a new, narrowly-scoped capability — a pattern for every future capability addition.
  • D-136 — Finance proxy is its own capability, not a reuse of Library's. The flat capability model treats each domain's proxy grant independently; confirmed as a settled pattern, not a one-off call.
  • D-137 — Edit and Void stay separate mechanisms. Void is for mistakes that shouldn't exist; Edit is for real transactions keyed in wrong.
