What Was Accomplished

It started as a bug report, not a feature request

Patrick reported the ledger was showing scouts and leaders as "present, but no credit" for events they'd actually attended and were previously linked correctly. Traced through direct SQL forensics (batch delete timestamps, the audit-trail deleted_reason column) to a real mechanism: a deleted duplicate calendar entry orphaned its ledger credit — event_attendance cascades on delete, but ledger_entries.calendar_entry_id only SET NULLs. The orphaned credit then looked like a stray duplicate in the Universal Ledger and got bulk-deleted for real, wiping Summer Camp credit for the whole roster.

Root cause, not a guess. Every step was verified against real production data before acting: the exact batch-delete timestamp and reason string, cross-referenced against event_attendance to confirm which credit rows were genuinely orphaned vs. legitimately duplicate. Recovered: 19 restored ledger rows, and along the way a second, unrelated duplicate was found and cleaned (a pre-existing Fast-Entry import colliding with the Roll-Call-linked credit) — plus a correction to the High Cliff transaction amount, which turned out to be a real error in the source spreadsheet itself, confirmed by Patrick.

Fixed at the source: calendar delete/merge safety (D-151)

deleteCalendarEntry now dry-runs first, reporting every attendance/ledger row that references the entry before anything is destroyed — same confirm-then-report pattern already used elsewhere in this codebase. New mergeCalendarEntries reassigns attendance, credit, resources, signup, and meeting agenda from a duplicate entry onto the one being kept, instead of deleting and hoping nothing was attached. It refuses outright — no guessing — when both entries have their own signup or meeting agenda.

The Roll Call & Ledger Reconciliation audit can fix what it finds (D-152)

Triggered by a specific finding — Veronica Kleinfeldt's missing credit had no way to resolve it from the audit page. This reverses a deliberate 2026-08-19 "read-only on purpose" decision, but only where it's actually safe to: credit_missing and date_drift each have exactly one right answer and now resolve in one click; credit_orphaned and qty_mismatch still offer both choices side by side rather than guess.

The actual Kind/Direction bug, found live and fully closed (D-153)

The 2026-08-19 fix for the Kind/Direction overlap complaint (D-147) turned out to be a real bug, not a UX nicety: the Record/Edit forms auto-set Direction whenever Kind changed to a value with a "usual" direction. Recategorizing the High Cliff transaction — a pure label fix — silently flipped its signed amount and corrupted the computed balance, with no warning at all (the auto-set fires FROM the mismatch, so the warning meant to catch it never got the chance).

Validated the underlying architecture was already sound. computeBalance and summarizeByActivity have only ever summed the signed amount — Kind was already irrelevant to the balance. The bug was purely a UI-layer coupling, now removed entirely. Kind carries no implied direction anywhere, permanently — a rule, not a preference.

Troop Finances reimport rewritten and re-run on production (D-154)

Column L (spreadsheet notes) had been silently dropped on the original import — read only to help guess a category, never written to memo. The "Who" memo also duplicated a name already captured via person_id. Rewrote the memo formula (notes preserved; Who's raw text appended only when it didn't resolve to a real person), extended person resolution to every row (not just scout accounts), and — since the import script had always connected via whatever env pointed at, which is never production — rebuilt it to read people from a plain CSV export and write a .sql file instead of connecting to any database directly.

Kind became a governed lookup table (D-155)

Patrick retired the confusing 'income'/'expense' Kind values via a new bulk-reassignment tool, then asked for a way to add a brand-new Kind on the spot. The old hardcoded 9-value CHECK constraint needed a code deploy for any change. New transaction_kinds table — same governance shape as the existing calendar_categories — makes Kind extensible from the admin UI, with real referential integrity (a rename cascades everywhere automatically; a Kind still in use can't be deleted). 'income' is gone as the first real use; 8 remain.

Finance ledger UX consolidated (D-156)

Record Transaction, Transfer, Reconciliation, and the new Manage Kinds panel were becoming four permanent on-page controls — Patrick: "too many buttons if we keep adding functionality." All four, plus Activity Report, Reimbursements, and Export CSV (moved out of header buttons), now live behind one "Actions…" pull-down that opens the picked function in a shared modal. Ledger search also gained date-range, amount-range (by magnitude, not sign — a $75 expense and a $75 payment both match "between $50 and $200"), and Activity contains-match filters.

Fixed a real UI bug along the way: admin sub-nav double-highlighting (D-157)

A screenshot showed both "Ledger" and "Activity Report" lit up at once in the Finance sub-nav — a section root's match path is itself a prefix of a sibling's. Fixed with a general longest-matching-path-wins rule, not a Finance-specific patch, so it covers this shape anywhere else it might exist in the admin nav.
