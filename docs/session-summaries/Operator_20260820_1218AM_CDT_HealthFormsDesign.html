What Was Accomplished

Question: how to secure family-uploaded health forms

Patrick asked how families could safely upload BSA Annual Health and Medical Record (AHMR) forms so a scoped subset of adult leaders could view them — without turning sensitive medical PII into a liability. Rather than answer from general best-practice knowledge, two specialists were consulted in parallel:

  • troop79-specialist mapped the actual current architecture — auth tiers, the person_capabilities permission model, the two existing storage mechanisms (public Bunny CDN vs. private Supabase Storage buckets), and prior decisions on sensitive fields.
  • qa-lead produced concrete, scale-appropriate security guidance — storage pattern, access-control model, retention, audit trail, and common mistakes to avoid — grounded directly in this codebase's existing patterns rather than a generic PII whitepaper.
Key finding: this feature reverses a prior, on-the-record decision. 20260713000000_demographics.sql states medical conditions and allergies are "deliberately NOT tracked — health form dates only, the forms themselves stay on paper with the health officer." Building this is a deliberate policy change, not an incidental side effect — flagged for Patrick's explicit sign-off before implementation.

Recommended design (reuse, don't invent)

The codebase already has two proven implementations of "sensitive file, scoped access, no public URL" — merit badge proof photos and finance reimbursement receipts. The recommendation is a third instance of the same pattern:

ConcernApproach
StorageNew private Supabase Storage bucket (health-forms), zero RLS policies, signed URLs only (5–10 min TTL). No Bunny CDN.
Access controlNew health_forms.view capability, excluded from the legacy LEADER_PASSWORD auto-grant — same pattern as finance.manage.
MetadataNew health_forms table with expires_at; reconcile against the existing people.health_form_date.
Retention~1-year expiry, surfaced via the existing attention-items.ts dashboard pattern. No auto-delete.
Audit trailLightweight access log, one row per signed-URL issuance, mirroring login_events.
