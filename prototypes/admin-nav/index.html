Admin Navigation — Current vs. Proposed

Same flat-section pattern sub-nav.tsx already uses (a section list has earned its keep for 10 volunteer leaders — see the plan for alternatives considered and rejected). The change is redistribution, not fewer clicks: the 7-item “Records” bucket splits into day-to-day recording vs. review/output, and the orphaned 1-item “Output” section folds into the new group instead of standing alone.

Mobile (375px) — the hidden bug

At 800px, admin.module.css sets .subNavSection { display: none; } so the sidebar becomes a flat wrapped row of chips for a phone/tablet at a troop meeting. All grouping disappears — today that means all 20 items (or however many the leader's role grants) sit in one undifferentiated wrap with no way to tell Finance from Setup. The proposed version keeps a compact inline divider so the groups survive the breakpoint.

Everything else — Overview, Entry, Planning, News & Events, Finance, Setup — is untouched: those sections were already reasonably sized (1–5 items) and their in-code comments document real intent (e.g. why Roll Call stays off the Calendar workbench) that a reorg shouldn't disturb without a concrete reason. Dashboard stays alone at the top deliberately — it's the landing page, not an orphaned item like Output was.

Alternatives considered

OptionVerdictWhy
Collapsible/accordion sectionsRejectedThis codebase has a documented production failure with <details>-based collapse (D-070, v1.19.0) — closed content became browser-internal “skipped content” that CSS !important couldn't override, and shipped broken twice before revert. A JS-driven (non-<details>) expand/collapse could avoid that specific failure, but with sections now capped at 5 items there's no scroll-length problem left to justify the added interaction cost.
Command palette / search (Cmd+K)RejectedSolves a discovery problem this audience doesn't have — 10 people who each use the same 3–5 items weekly. Adds a keyboard-first affordance to a non-technical, often-on-a-tablet user base.
Top-level tabs instead of sectionsRejectedMakes the narrow-capability collapse worse, not better: a calendar.write-only leader would land on a mostly-empty tab instead of a short, honest 2-item list. Also a bigger engineering lift (routing/state) for a site this size.
Icons per sectionHeld / optionalCould aid scanning, but is a real ongoing maintenance surface (every future nav item needs an icon decision) for a marginal gain over the existing 3px active-border accent. Flagged as an open question, not built into this prototype.
