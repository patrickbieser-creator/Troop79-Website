What this prototype replaces

Today /library/mb/[mbId] renders four stacked sections after the header: Scout Progress grid → Requirements tree → Whole-badge resources (+ one SectionDivider per top-level requirement that has resources) → an “I did this” radio picker listing every leaf again. The last three all enumerate the same requirement codes. This prototype keeps the header, stats and grid unchanged and folds the other three into one list whose row grammar is: code · label · who-chips · [resources] · [counselor note] · actions. Whole-badge resources sit at the top of the same list as a “For the whole badge” row (ghost MB tag) — no separate divider.

Plan: attaching a video / link / doc to ONE requirement

The schema already has the address (mb_req + {mbId}-{code}) and the page already fetches every mb_req placement for the badge with one LIKE 'chemistry-%' query. What is missing is the entry point and the display granularity.

  1. Entry point. The row’s Suggest action passes target=mb_req:{mbId}-{code}. The submit flow validates the code exists in merit_badge_requirements for that badge (leaf or top-level), shows the target read-only at the top of the form (as the dialog here does) with a “wrong requirement? go back” link. No free-text target picking.
  2. Write. Submit inserts library_resources (status=pending, submitted_person_id from the session, submitted_by_label) and its library_placements row in the same transaction. The placement exists from the start so the review queue and the submitter’s pending line both know where it belongs; public reads are already filtered on library_resources.status, so nothing leaks.
  3. Display. In page.tsx, replace the byTopCode grouping (topLevelCodeOf) with an exact-code map; a placement on a top-level code renders on the group header row. Delete the per-top-level SectionDivider blocks, the whole-badge ResourceCard list, and MbProofPicker; the tree component grows the sub-row and actions.
  4. Submitter’s pending line. One extra query when a family/leader session is present: pending resources for this badge where submitted_person_id = the viewer. Visitors have no identity, so their “sent for review” is the dialog’s success state only.
  5. Review queue. Show the target as “Chemistry › 4c — Flame tests”; allow the webmaster to re-target (edit the placement) and pin/sort before approving — both already exist at the placement level.
  6. Notes. The narrative editor in /admin/library gains a requirement picker so a counselor note can be saved on an mb_req target; this page loads them with the same LIKE pattern as placements.
  7. Rank page. /library/rank/[rankId] adopts the identical row grammar with rank_req + {rankId}-{code}; the per-leaf route can then link to the row anchor instead of a separate page. Not built here.

States demonstrated

  • Viewer: scout (own chips, I did this), parent with two scouts (two chips per row, scout picker in the proof dialog), visitor (no chips, no I did this, Suggest available, sign-in hint).
  • Rows: 4c has three resources incl. a pinned YouTube thumbnail and (for the parent) a pending suggestion; 2c and 4d carry counselor notes; req 4 has a group-level document; req 8 is “do any one of”; 6 has nothing (renders nothing extra).
  • Proof dialog: scout picker (done scouts disabled, pending scouts disabled), photo / written report / link, inline validation error, Sending… (700 ms mock), success with what-happens-next, row chip flips to ⏳.
  • Suggest dialog: kind (video / link / document / image), URL or file (file only for document/image), title, note, submitter name for visitors, validation, Sending…, “Sent for review”, pending line appears in the row for this viewer only.
  • Collapse/expand: per group and all-at-once; collapsed header shows “4 parts · 3 resources · 1 note”. Button + hidden, not <details> (D-070).

Interaction spec

  • Chevron rotate 180 ms ease; dialog fade/slide 150 ms ease-out; new pending line 180 ms rise. No other motion.
  • Actions: 12 px Open Sans 700 text buttons, forest for I did this, navy for Suggest; hover = cream fill. ≤ 640 px: icon only (✓ / +), label returns on focus-visible and hover, aria-label always present, 30 px min target.
  • Focus: :focus-visible ring on every control (navy-light 2 px, 2 px offset). Dialogs are native showModal() — focus trap, Esc, and focus return come free. Success is announced through a polite live region.
  • Rows are a CSS grid: tag / text / actions, with the sub-row spanning text + actions. Children indent 26 px (12 px on phones). The list is designed to hold 80+ leaves (First Aid) without a wall: one line per resource, notes one line, chips ≤ 2 per row for a family.

What is mocked

  • All data is in-page JS; nothing persists past a reload. Names, household, counselor and resources are invented. Requirement text is BSA’s (paraphrased, as in production).
  • YouTube thumbnails are inline SVG placeholders; production uses resourceThumbnail().
  • Photo upload accepts a file but never reads it. Proof and suggestions are appended to in-memory arrays; “Reset demo data” restores the seed.
  • The site nav and footer are stand-ins. The masthead’s “signed in as” reflects the viewer toggle.

Open questions

  1. Scout-login proof: Family-Identity-Auth Phase 0 refuses proof from a scout session. This prototype shows “I did this” enabled for the scout viewer (per the brief). Should production grey it with “ask a parent” instead?
  2. Should the suggest form allow re-targeting within the badge (a requirement dropdown), or stay strictly pre-targeted with a go-back link?
  3. Do group-level placements (chemistry-4) remain allowed, or must every resource attach to a leaf? Existing placements were grouped by top-level code; a leaf-only rule needs a migration pass.
  4. Visitors can suggest today via /library/submit; does a visitor need to leave an email for follow-up, or is a name label enough?
