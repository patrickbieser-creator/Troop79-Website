Concept

A persistent header, tabs (Overview / Details / Contact & sign-in / Household & family / Roles / History) and one always-editable form spread across them. Any draft edit anywhere lights one sticky footer — "Save 3 changes · Discard" — and marks the tabs that hold edits with a dot. Status and household are ordinary draft fields. Lists that commit on click (emails, family, roles) keep the dashed "Takes effect immediately" treatment so the two models are never confused. History is a real change log. This is Jenna's Direction 2 flavour with Direction 3's tabs and log.

What it fixes (Jenna's numbering)

  • #1 One Save on the page, always in the same place, and it only appears when there is something to save. It follows the house standard exactly: label says the state, Saving → Done.
  • #2 Status is a draft field for scouts and adults alike, saved by the same bar, with the same reason rule (scout: required list; adult: optional text).
  • #3 Parents/guardians are outside the draft and say so; Discard never claims to undo them.
  • #4 Merge and Delete both confirm with consequences (Overview → Danger zone).
  • #5 Household is a draft field; the edited field shows "was: Whitlock (Dana & Marcus)" and the change is listed by name in the save bar before it lands. After saving it is in History.
  • #6 End role confirms; Grant role announces the tab move.
  • #7 No standing hints; one "How this works" disclosure per tab.

States and transitions

  • Save bar: hidden (draft = saved) → dirty ("Save N changes" + "Discard", lists the changed fields by name and tab) → invalid (red top border, "Fix 1 problem on Details" jumps to the field, Save disabled with a title) → saving ("Saving changes…", controls disabled) → done (green, "Done — saved 3 changes", 1.5 s) → hidden.
  • Fields with an unsaved edit get a gold left rule and "· edited" in the label, plus "was: …" under it. Tab labels get a gold dot with the count; a red dot when a field on that tab is invalid.
  • Discard reverts everything to the last save at once and toasts "Discarded 3 changes · Undo" (8 s), so a mis-click cannot lose work.
  • Back to roster or opening another person while dirty → confirm "Save, discard, or stay?" (three-way, since the edit may span tabs the user has forgotten).
  • Pending update: whole request reviewed on Overview (Current / Proposed table, Approve / Reject with reason); the tabs whose fields it touches show a "1 pending" chip that jumps to Overview. Approving writes straight to the record (it is the family's proposal, not the leader's draft) and appears in History.
  • History: seeded entries (created, import, YPT, past status changes) plus every save, approval, role and email change made in this session, highlighted green.
  • Send sign-in link / emails / family / roles / merge / delete / promote: as in A.

Timings

  • Round-trip 600 ms mocked. Save bar slides 200 ms ease. Done state 1.5 s. Undo window 8 s.

Responsive

  • Single column throughout; tabs scroll horizontally on narrow screens; the save bar is full-width and the toast sits above it. Body has bottom padding so the bar never covers the last field. No horizontal scroll at 375 px.

Accessibility

  • Tabs are role=tab with aria-selected; the save bar is a labelled region and its text changes are announced via the toast's role=status; changed fields are marked in text ("· edited", "was: …"), not only colour. Native dialog for confirms. Visible focus everywhere.

What is mocked

  • All server actions (600 ms, succeed). History seed is invented. The three-way leave dialog's "Save" path validates first and stays if invalid. No cross-leader conflict detection.

Deviations / open questions

  • Roles are an immediate list here, not a draft — a role grant moves someone between tabs and the roster needs to know at once; batching it into the save bar felt dishonest. Could be revisited.
  • This direction needs a real change-log table and one atomic "save person" server action that touches people + scouts + household_members in one transaction — the highest build cost of the three.
  • Pending updates stay whole-request (today's model) — the one direction where no server change to change requests is implied.
