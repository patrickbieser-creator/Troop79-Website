How else might the photo library be presented?

Six working answers, on one scroll. Every concept below runs on the real fourteen albums currently in photo_albums, uses only public design tokens from globals.css, and links out to Google Photos the way the real page does. Hover things — the interactions are real.

How to read this page

  • Concept 0 is today's page, rebuilt here so you can compare against it without switching tabs.
  • Each concept has a live demo in a bordered canvas, then an annotation strip: what it optimizes for, how chronology survives, what happens to description and photo count, image weight, and build effort.
  • The four hard requirements are called out per concept:
Date Title Category Chronology

Three facts that shaped every concept

  • The library is small — 14 albums, not 60. A three-across card grid inside year groups is a layout for a library five times this size. 2022 has 2 albums and 2025 has 3; in a 3-column grid those years render as a broken row.
  • There is a real two-year hole: no albums at all for 2023 or 2024. Any timeline-shaped design will show that hole honestly. That's a content decision, not a design bug — see the open questions.
  • Covers are the page's whole weight budget. Fourteen 1–4 MB PNGs is roughly 25 MB above the fold. Every concept here is annotated for image weight, and two of them work with none.

Bug found while reading the code

albums-browser.tsx hardcodes a CATEGORY_CLASS map from category label to a palette token — but the categories themselves live in calendar_categories, which already carries an authoritative color column that the calendar renders (month-grid.tsx, colors: CategoryColorMap). The map is missing five live labels. "Troop 79 — 2025 in Review" is Recruiting / Outreach, which has no entry, so it silently falls through to the default navy chip instead of its DB color #a04a3d. Every concept below reads the DB color instead, the way the calendar does. That alone is a same-day fix, independent of which concept you pick.

Today — Year-grouped card grid

The baseline. Reproduced here at real data volume so the comparison is fair rather than remembered.

Shipped
Live demo — current design
What it optimizes for
Cover photography. The image is 60% of the card and the first thing you see.
Chronology
Kept — year headings, newest first. This part already works and every concept preserves it.
Description & count
Both shown. Description is 2-line clamped and null on 2 of 14 albums, so the cards are visibly uneven.
Image weight
Worst case. Every album loads a full-size cover, all above the fold at 14 albums.
The actual problem
Identical recipe to a news card — 16:10 box, 17px Playfair title, meta line, hover lift. Nothing signals this is 209 photos rather than this is an article.

The Spine

Stop grouping by time and start drawing time: one continuous rail down the page, every album a dated node on it, gaps included.

~1 day
Live demo — hover a row
What it optimizes for
Narrative. Reads as the troop's history rather than a catalog — which is what a family actually wants from four years of photos.
Chronology
Strongest of the six. The layout is the timeline. Day-level dates on the rail, not just month; the 2023–24 gap is rendered as a labelled dashed segment instead of quietly vanishing.
Date / Title / Category
Date on the rail in display type. Title in Open Sans at 15px — sans, so Playfair stays the story voice. Category is the rail node's color plus a chip.
Description & count
Description dropped. Count kept as a quiet meta item — it's the one number that earns its place.
Image weight
Very low. One 60px square per row → a 120px derivative, ~6 KB each, ~85 KB total. Two orders of magnitude under today.
Build effort
New CSS module + a light restructure of the map in albums-browser.tsx. No query changes. The gap marker needs a tiny "years with zero albums" derivation.

The Print Shelf

Make an album look like a stack of prints, not a story card — white border, 4:3 print geometry, two sheets peeking out behind, category as a sticker on the corner.

~half a day (+ image pipeline)
Live demo — hover a print; the stack fans and it straightens
What it optimizes for
The exact problem you flagged: album cards reading as news stories. The stack silhouette does that in two pseudo-elements and no extra markup.
Chronology
Kept as today — year heading + newest-first within year. Every caption also carries a full date, so a print is self-dating even out of context.
Date / Title / Category
Date sits in the print's bottom margin where a photo-lab date stamp goes. Title in Open Sans 13px bold. Category is a colored sticker overhanging the top-right corner — visible before you read anything.
Description & count
Description dropped — it's what makes these look like articles. Count kept, small, in the caption foot.
Image weight
Same count, much smaller. 4-up at 4:3 means a ~280px-wide derivative. This concept is the one that requires the image pipeline — at 1–4 MB PNGs it's no better than today.
Build effort
Cheapest real win. Same JSX shape as the current card; almost entirely a rewrite of photos.module.css. The stack pseudo-elements drop at 2-up on phones where they cost more than they earn.
3

The Ledger

Trade every image for scanability: fourteen albums as a sortable index that loads in zero bytes and reads top-to-bottom in one glance.

~half a day
Live demo — click a column header to sort; toggle thumbnails on
Sorted by date, newest first
What it optimizes for
Finding a specific album, and honest comparison. "Which outing has the most photos?" is answerable in one look — the bar makes 1,024 vs 5 a visible fact instead of a number to parse.
Chronology
Kept, and defended. Default sort is date descending with year separator rows. Sorting by another column is opt-in, the date column never leaves, and the year rows reappear the moment you sort back. aria-sort announces the state.
Date / Title / Category
All four are literally columns. Date is exact (no "May 2026" fuzz). Category is a DB-colored dot plus its label — colored text at 12px still clears 4.5:1 on cream.
Description & count
Description dropped entirely. Count promoted to a first-class sortable column with a proportional bar.
Image weight
Zero by default. The thumbnail toggle lazily swaps in 38px squares only if asked. This is the concept that survives a bad connection at a campsite.
Build effort
Low. A real <table>, existing data, no new query. Best accessibility of the six by a wide margin — it's tabular data presented as a table.
4

The Year Shelf

One horizontal shelf per year. A two-album year looks deliberate on a shelf; in a three-column grid it looks broken.

~1 day
Live demo — drag, scroll, or use the arrows; tiles are keyboard-reachable
What it optimizes for
Sparse and uneven years — which is exactly what this library is and will stay. It also scales the other way: a 25-album year just makes a longer shelf, never a wall.
Chronology
Kept on two axes. Shelves descend by year; tiles run newest→oldest left to right. Risk to watch: horizontal order is a weaker time signal than vertical, so each tile carries its own full date in the overlay.
Date / Title / Category
Date and title in the gradient overlay; category as a sticker top-left; count as a pill top-right. Everything is legible without hovering.
Description & count
Description dropped — no room, and a square tile is better for it. Count kept as the corner pill.
Image weight
Best of the image-led concepts. Off-screen tiles are genuinely off-screen: horizontal overflow plus loading="lazy" means a year's fourth-through-tenth albums never fetch until scrolled.
Build effort
Medium. The layout is easy; the accessibility is the work — scroll containers need a keyboard path, a visible scrollbar, and arrow buttons that disable at the ends. Budget the extra half day for that, not for the CSS.
5

The Almanac

Years down, seasons across. A troop's year rhymes — Klondike in January, camp in July, Court of Honor in the fall — and no other layout can show that.

~1.5–2 days
Live demo — read down a column to see the same thing happening every year
What it optimizes for
Institutional memory. It answers a question no other view can: "what do we do every winter?" For a family deciding whether to join, that's the most persuasive page on the site.
Chronology
Kept, and enriched. Reading order is still strictly chronological (down = years, across = seasons in order), but a second, cyclical time axis appears for free.
Date / Title / Category
Day-and-month per item, title in Open Sans 12px, category as the item's left border color. Dense but not cramped.
Description & count
Description dropped. Count kept as a small trailing number.
Image weight
Zero. Text-first by design — there is no cell geometry that a cover fits into without wrecking the grid.
Honest risk
It is mostly empty today. Five year-rows × four seasons = 20 cells, and the fourteen albums fill only 7 of them — the 2023 and 2024 rows are entirely blank, and 2022 and 2025 each light up two. This design gets better every year and is weakest right now. Mobile also has to collapse it to a single column, at which point it's Concept 1 with worse dates.
Unresolved: where seasons start
The columns are calendar quarters, because that's the only cut where left-to-right stays forward in time. The cost shows in the demo: Court of Honor, September 7, lands under "Summer" — which no scouting family would say. True seasons (Dec–Feb winter) would fix that and break chronology, since December would belong to the following winter. Needs your call before this one could ship.
6

One Index, Three Lenses

Don't pick one. Keep a single filtered result set and let the visitor choose how it's drawn — prints for browsing, timeline for history, list for finding.

Sum of the two you ship + ~2 hrs
Live demo — the filter and the view toggle work together; try Category = Campout, then switch views
What it optimizes for
The fact that the same page serves three different errands: a parent browsing after a campout, a new family reading the troop's history, and someone hunting for "that Klondike album."
Chronology
Kept in all three lenses — that's the constraint that makes them interchangeable. Switching views never reorders the data, only redraws it.
Description & count
Description dropped everywhere. Count present in all three, most prominent in List.
Image weight
Visitor-controlled, which is the real answer. Default to Prints on desktop and remember the choice; anyone on a slow connection lands on List once and stays there.
Build effort
The toggle itself is trivial — ~2 hours: one view state, one more URL param alongside the existing ?category=&year=&q=, and a localStorage read on mount. The cost is whichever views you build.
Recommendation
Ship Prints + List first. Prints fixes the identity problem for ~half a day of CSS; List fixes weight, scanning and accessibility for another half. Timeline is the nicest of the six and can follow when there's appetite.

Recommendation

Ship Concept 2 (Print Shelf) as the default view and Concept 3 (Ledger) as the alternate, joined by Concept 6's toggle. Concept 2 solves the stated problem — album cards reading as news stories — with a CSS rewrite over markup that already exists, which is about half a day. Concept 3 solves the weight, scanning and accessibility problems with a real table and no images, for another half day. The toggle costs two hours and lets the page serve browsing and finding without either one compromising. Concept 1 (Spine) is the most beautiful of the six and the strongest on chronology; it is the right third lens once the first two are live, not the thing to start with.

Do this first, regardless of which concept wins

  1. Fix the category color source. Delete CATEGORY_CLASS from albums-browser.tsx and read calendar_categories.color the way month-grid.tsx already does. Five labels are unmapped today; one of them is live on the "2025 in Review" album. Same-day fix, no design dependency.
  2. Settle the cover-image pipeline. Nothing else on this page matters as much. Concepts 2 and 4 are only wins if a cover ships at ~40 KB instead of 1–4 MB.

Open questions — I need answers to these before building

  1. 2023 and 2024 have no albums at all. Are those photos missing from the site, or did they genuinely never get collected? Concepts 1, 4 and 5 all make that hole loud and visible. If they exist somewhere, adding them changes which concept wins; if they don't, do you want the gap labelled honestly ("no albums posted") or quietly skipped?
  2. Can we resize covers? lib/bunny-storage.ts talks to a Bunny Storage zone — I found no evidence of Bunny Optimizer or any ?width= transform in the codebase. So thumbnails mean either enabling the Optimizer add-on (a paid Bunny feature, needs your call) or generating derivatives at upload time in the admin uploader. Which?
  3. Is description worth keeping? Two of fourteen are null and several restate the title verbatim ("Crossover from Pack 179 at Grant Park", "Chess Merit Badge"). Every concept here drops or demotes it. Do we retire the field, or make it required and useful on entry?
  4. How much do you trust photo_count? The type comment calls it leader-maintained and approximate, and "2025 in Review" claims 1,024. Concept 3 promotes it to a sortable column with a proportional bar, which is only a good idea if the number is roughly right. Promote, or drop?
  5. Default view and persistence. If we ship the toggle: default to Prints everywhere, or List on phones? And should the choice persist per visitor in localStorage, or live only in the URL alongside the existing ?category=&year=&q= params?
  6. Only if the Almanac interests you: where does a season start? I used calendar quarters so that reading across a row stays forward in time, but that files the September Court of Honor under "Summer." Real seasons read better and break the chronology guarantee. Not worth solving unless Concept 5 is in play.
  7. Uniform treatment, or a hero? Right now every album gets the same weight. Should the newest album — or a leader-flagged one — get a larger slot at the top? That needs a new featured boolean on photo_albums, so it's a schema question, not a CSS one.

Considered and rejected

  • A map view. Genuinely appealing for a troop — Governor Dodge, Long Lake, Boundary Waters, Tesomas are all real places. Rejected because photo_albums has no location field and no lat/long anywhere in the schema. It would need a new column plus back-filling fourteen rows by hand. Worth revisiting as its own plan; not a restyle.
  • Masonry / mixed-height mosaic. Rejected on two counts: it needs more large images visible at once, which is the wrong direction for this page, and it actively damages chronology — a masonry column flow means the reading order and the date order stop agreeing.
  • Infinite-scroll feed. Fourteen albums. There is nothing to paginate.

Token discipline note

Every color, size, space and radius in this file comes from globals.css. No new tokens are required for any concept. The nine category colors are database rows (calendar_categories.color), not CSS tokens — they belong in a dynamic inline style with a /* dynamic */ comment, exactly as admin/(workspace)/events/page.tsx already does. I checked all nine against white: the lightest, #527554, lands at 5.25:1, so the solid chips clear WCAG AA. The text-only variant on cream clears 4.8:1. If any concept ships, its specimen goes on /admin/styleguide/public in the same commit.
