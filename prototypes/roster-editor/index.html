Scout Editor — Section Chrome & Wayfinding

Today, all 6 sections (Identity, Demographics, Contact, Things We Should Know, Parents/Guardians, Status) use the exact same dashed 1px divider and an 11px uppercase label — that’s the entire visual distinction between them in a dialog dense enough to need scrolling. The proposed version keeps every field visible in one scroll (no hide/collapse of any kind — see the callout below on why) and adds a sticky left-rail jump-nav plus stronger per-section chrome.

This tab toggle is prototype-comparison chrome only, not part of the recommendation — both mocks render the full form; the button just swaps which one is on screen for you to compare.

Why not an accordion? Tracker memory (v1.19.0, D-070) documents a production incident where a per-rank <details> accordion shipped broken twice: a closed <details>’s content is browser-internal “skipped content,” not a normal CSS value — display: block !important and content-visibility: visible !important both failed to force it visible, and every rank but the current one rendered blank in production. The proposed treatment above never hides a section at all — the rail is pure additive wayfinding (scroll-to / highlight-on-scroll), so every field stays in the DOM, visible, and part of the one native <dialog> form the whole time. If a tabbed variant (one section visible, others hidden) is wanted instead, that's a different, riskier trade — flagged as an open question in the plan, not built here.

Ripple effect on the ~7 shared lookups.module.css editors

This treatment is designed to be low-blast-radius by construction, not by accident:

ChangeScopeWhy it doesn't ripple
Section card chrome (tint / left border / numbered badge)New opt-in class, e.g. .editSectionCard, added alongside the existing .editSection in lookups.module.cssExisting dialogs (MB editor, Event editor, etc.) keep rendering with today's dashed-divider .editSection unless a component explicitly switches classes. Nothing changes for them until Patrick decides to.
Sticky rail + scroll-spyNew markup + a small script, scoped to scout-form.tsx only (candidate: adult-form.tsx if it grows past ~1 section)Not a shared CSS class at all — it's specific to dialogs dense enough to need it. A 1–2-section lookup editor (most of the 7) has nothing to jump between.
.editGrid / .editField / .editLabel / .editInputUnchangedThe field-level markup that every one of the ~7 other editors relies on is untouched by this proposal.

Recommendation stated explicitly (per the brief's ask): roll the stronger section-card chrome out to all multi-section editors eventually — it's a strict visual upgrade and costs little even on a 1-section dialog — but gate the rail nav on a threshold (4+ sections) rather than rolling it out module-wide. Most Lookups editors have 1–2 sections and would gain nothing from a rail; scout-form.tsx (6 sections) and possibly people-table.tsx's PersonEditor (also dense, per the consistency audit) are the real candidates.
